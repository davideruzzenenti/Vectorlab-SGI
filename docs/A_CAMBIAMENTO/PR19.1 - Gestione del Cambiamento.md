## 1 Scopo

Stabilisce come Vectorlab pianifica, approva e registra i cambiamenti ai
propri sistemi informatici e al Sistema di Gestione Integrato, in modo
che nessun cambiamento riduca la sicurezza delle informazioni o la
qualità del servizio senza che qualcuno l'abbia valutato.

## 2 Campo di applicazione

- **Cambiamenti ai sistemi di Vectorlab**: server Aruba e servizi che
  ospita (n8n, siti web, strumenti interni), Google Workspace, organizzazione
  GitHub, ClickUp, rete dell'ufficio. Esempi: aggiornamento del server,
  nuovo servizio, cambio di configurazione o di permessi amministrativi,
  dismissione di un sistema.
- **Cambiamenti al Sistema di Gestione**: organizzazione e ruoli, processi,
  campo di applicazione, fornitori critici, documenti del sistema.

Non rientrano:

- i cambiamenti ai sistemi dei clienti, che seguono le regole del cliente
  ([PR35.1](../8.2_PRODOTTI%20%26%20SERVIZI/PR35.1%20-%20Digital.md));
- le modifiche al codice nei progetti, che seguono il ciclo di sviluppo
  con revisione del codice ([PO25](../A_PROGETTAZIONE%20%26%20SVILUPPO%20SICURO/PO25%20-%20Sviluppo%20Sicuro.md), [PR35.1](../8.2_PRODOTTI%20%26%20SERVIZI/PR35.1%20-%20Digital.md)).

## 4 Responsabilità

| Ruolo | Compiti |
| --- | --- |
| System Administrator esterno | Esegue e registra i cambiamenti ai sistemi; propone quelli importanti |
| CTO | Approva i cambiamenti importanti ai sistemi; viene informato di quelli urgenti |
| RSGI | Valuta i cambiamenti al Sistema di Gestione e aggiorna documenti e analisi dei rischi |
| Amministratore Unico | Approva i cambiamenti al Sistema di Gestione |

## 5 Cambiamenti ai sistemi

**Regola**: sul server non si fanno modifiche a mano. Ogni cambiamento è un
commit nel repository dell'infrastruttura (Ansible, GitHub aziendale),
provato prima sul portatile di chi lo fa e applicato dalla CI. Così ogni
cambiamento è tracciato e riproducibile ([PR32.1](../A_ASSET%20%26%20CONFIGURAZIONE/PR32.1%20-%20Gestione%20delle%20Configurazioni%20e%20dell%27Infrastruttura%20IT.md)). Gli accessi in sola
lettura per una verifica (es. controllare le regole del firewall) non sono
cambiamenti.

Gli strumenti interni si sviluppano in locale, con dati finti salvo diversa
indicazione del cliente, e arrivano in produzione solo come immagini Docker
distribuite dalla CI. Per strumenti di queste dimensioni non c'è un
ambiente di prova separato: la prova si fa in locale.

| Tipo | Esempi | Come si esegue e si approva | Registrazione |
| --- | --- | --- | --- |
| **Ordinario** | Aggiornamenti di sicurezza e di versione ([PR32.1](../A_ASSET%20%26%20CONFIGURAZIONE/PR32.1%20-%20Gestione%20delle%20Configurazioni%20e%20dell%27Infrastruttura%20IT.md) §7); piccole modifiche di configurazione senza effetto sulla sicurezza | Commit nel repository, applicato dalla CI. Già approvato da questa procedura | Storico Git del repository |
| **Importante** | Modifica di firewall, porte esposte, accessi amministrativi, backup, cifratura o certificati; nuovo servizio o dismissione; migrazione; cambio di fornitore | **Pull request** nel repository, rivista e approvata da una persona diversa da chi l'ha scritta (CTO o System Administrator) prima di applicarla | Pull request su GitHub |
| **Urgente** | Correzione di una falla critica o di un guasto in corso | Commit applicato subito dalla CI; il CTO viene informato. Entro 2 giorni lavorativi la modifica viene rivista come una pull request | Storico Git e revisione a posteriori |
| **Da console** | Pannello Aruba, DNS, console di amministrazione di Google Workspace, impostazioni dell'organizzazione GitHub: tutto ciò che non passa da Ansible | Secondo il tipo (ordinario, importante, urgente) | Log di audit del fornitore; per i cambiamenti importanti anche un task nella lista ClickUp «Server» (cartella Evidenze) |

Per un cambiamento **importante** la pull request o il task contiene:

1. cosa si cambia e perché;
2. effetti sulla sicurezza: accessi, backup, log, esposizione su
   internet, dati personali;
3. come si torna indietro se qualcosa va male (di solito: annullare il
   commit e riapplicare la configurazione, oppure ripristinare la copia
   del server, [PR21.1](../A_BACKUP%20%26%20RESTORE/PR21.1%20-%20Gestione%20dei%20Backup%20e%20Restore.md));
4. l'approvazione di chi l'ha rivista.

Dopo l'esecuzione si verifica il risultato (es. i servizi ripartono, la
scansione non trova nuove porte o falle). Se il cambiamento modifica
l'esposizione ai rischi, RSGI aggiorna l'analisi dei rischi
([PR33.1](../6.1_ANALISI%20DEI%20RISCHI/PR33.1%20-%20Processo%20Analisi%20del%20Rischio%20e%20Trattamento.md)).

I workflow di n8n si modificano solo dall'interfaccia di n8n, in produzione,
senza copia in un repository Git: rischio accettato dall'Amministratore Unico.

## 6 Cambiamenti al Sistema di Gestione

Quando serve un cambiamento al Sistema di Gestione (per esempio un nuovo
ruolo, un nuovo processo, un fornitore critico che cambia, un'estensione
del campo di applicazione):

1. RSGI ne valuta lo scopo, le conseguenze, le risorse necessarie e chi
   ha la responsabilità, verificando che il Sistema resti integro;
2. l'Amministratore Unico lo approva;
3. RSGI aggiorna documenti ([PR08.1](../7.5_INFORMAZIONI%20DOCUMENTATE/PR08.1%20-%20Gestione%20Informazioni%20Documentate.md)), analisi dei rischi e comunicazioni
   al personale;
4. il cambiamento si registra nella lista ClickUp «Non conformità e
   miglioramento» e si riporta nel Riesame della Direzione ([PR12.1](../9.3_RIESAME%20DIREZIONE/PR12.1%20-%20Riesame%20della%20Direzione.md)).

## 7 Registrazioni

| Registrazione | Dove | Chi | Conservazione |
| --- | --- | --- | --- |
| Cambiamenti ai sistemi (ordinari e urgenti) | Storico Git del repository dell'infrastruttura | System Administrator | Per tutta la vita del repository |
| Cambiamenti importanti | Pull request nel repository; per quelli da console, task nella lista ClickUp «Server» | System Administrator, CTO | Per tutta la vita del repository; task 3 anni |
| Cambiamenti da console | Log di audit di Google Workspace, GitHub e Aruba | Fornitore | Secondo le condizioni del fornitore |
| Cambiamenti al Sistema di Gestione | Lista ClickUp «Non conformità e miglioramento»; Riesame della Direzione | RSGI | 3 anni |
